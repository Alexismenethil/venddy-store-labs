# Restricciones

Las restricciones conservan tecnologías y condiciones del sistema existente, y delimitan el diseño aprobado para el lanzamiento. Las decisiones objetivo requieren implementación y validación; no describen una migración ya ejecutada.

| ID | Restricción | Descripción |
| :--- | :--- | :--- |
| RC01 | Aplicación web con conexión a internet | Venddy se utiliza desde un navegador en web, móvil o terminal POS. La carta por QR no exige instalar una aplicación ni registrar al comensal; el flujo operativo requiere conexión a internet. No se ofrece operación sin conexión en este alcance. |
| RC02 | Continuidad del stack existente | Se conservan Next.js y React en frontend; Node.js, Express y Socket.IO en backend; Prisma y PostgreSQL para persistencia. El monorepo mantiene frontend, backend, core y shared. El diseño del lanzamiento no exige sustituir esas tecnologías. |
| RC03 | REST y comunicación en tiempo real | El frontend consulta y opera mediante la API HTTP/REST. Socket.IO comunica cambios operativos por empresa; los eventos se emiten después de confirmar la transacción y el cliente relee el estado por REST al reconectar. |
| RC04 | Aislamiento obligatorio entre negocios | La empresa se resuelve por un subdominio registrado antes de validar sesión y permisos. Datos, claves de idempotencia, salas y caché conservan el contexto empresarial. PostgreSQL aplica RLS con roles separados de operación, plataforma y administración; la cartera transversal corresponde solo al proveedor y al soporte autorizado. |
| RC05 | Una sola API en el lanzamiento | El objetivo utiliza Render Starter en Virginia, una instancia de 0,5 CPU y 512 MB. No incorpora Redis ni un balanceador adicional. La memoria, los pools y la concurrencia deben ajustarse y medirse; esa instancia no ofrece continuidad ante su propia caída. |
| RC06 | Migración de frontend condicionada | El objetivo sitúa Next.js en Cloudflare Workers Paid con OpenNext. La compatibilidad de la versión, `nodejs_compat` y el soporte experimental de `proxy.ts` deben probarse en workerd junto con SSR, subdominios, Google, cookies, imágenes y Socket.IO. El cambio de DNS queda condicionado a esas pruebas y a una ruta de reversión. |
| RC07 | PostgreSQL como fuente de verdad | Pedidos, cobros y stock se confirman en la base principal de Neon Launch, AWS us-east-1, con referencia inicial de 0,25 CU, pooler operativo y recuperación a un punto en el tiempo de siete días. Su capacidad y consumo se ajustarán a mediciones. La caché y los eventos no reemplazan la persistencia ni sus transacciones. |
| RC08 | Separación de medios públicos y respaldos | Las fotografías objetivo se guardan en Cloudflare R2 Standard y se sirven por un dominio personalizado con CDN, variantes y URLs inmutables. Los respaldos usan un bucket privado y credenciales independientes; no pueden quedar expuestos mediante el dominio de imágenes. |
| RC09 | Servicios y cargos de referencia | La edición aprobada del 2 de octubre de 2026 contempla Workers Paid con base de US$5/mes, API Render Starter de US$7/mes y Render Cron con mínimo de US$1/mes, facturado según el tiempo de ejecución. Neon Launch se paga por consumo; R2, GitHub Actions, Sentry Developer y UptimeRobot Free se aprovechan dentro de sus cuotas. Se controlan excedentes y límites; las tarifas no equivalen a un total fijo garantizado. |
| RC10 | Control de versiones y release separado | El código se mantiene en Git; CI verifica tipos, lint, pruebas y build. La mejora objetivo conecta esas verificaciones con una compuerta de despliegue y una etapa de migraciones con credenciales distintas de las de operación. |
| RC11 | Conservación de SQL y roles | Las migraciones deben preservar funciones `facipos.*`, políticas RLS, permisos y restricciones que Prisma no representa. Los respaldos y la restauración recrean los roles necesarios; `pg_dump` de una base no respalda por sí solo los roles globales. |
| RC12 | Comprobantes y pagos dentro del alcance | El sistema registra cobros y medios de pago, y genera notas de venta internas. No se presenta como pasarela de pagos ni como emisor de boletas o facturas electrónicas validadas por SUNAT. Esas integraciones necesitarían un alcance y diseño propios. |
| RC13 | Recuperación manual y verificable | El objetivo programa copias diarias y ensayos semanales en un proyecto separado de Neon Launch bajo demanda. La recuperación no es una réplica en servicio ni una conmutación automática. RPO de 24 horas y RTO de 2 horas para la copia externa son metas que deben medirse. |
| RC14 | Monolito modular como base del lanzamiento | Se conservan tres capas y se completan puertos y adaptadores en el backend. La hexagonalización todavía es una mejora objetivo. Los módulos no se despliegan como microservicios; una extracción o más instancias requieren una necesidad y resultados de carga demostrados. |

El despliegue **actual** permanece documentado como Vercel Hobby, API principal Render Free en Oregon, PostgreSQL en Neon y fotografías en Cloudinary Free. No debe sustituirse por el objetivo al describir lo que está en ejecución. La [arquitectura inicial](../arquitectura/arquitectura-inicial.md) mantiene ambas vistas.
