# Atributos de calidad

Los atributos AC01 a AC10 corresponden, en el mismo orden, a RNF-01 a RNF-10 del informe oficial de Venddy. Cada escenario define un estímulo, su contexto y la respuesta esperada; los criterios deben comprobarse antes de aceptar el lanzamiento.

**Estados:** Actual indica un control presente en el código revisado; Objetivo, una mejora pendiente; A validar, una condición que requiere ensayo en la infraestructura prevista. Ninguno de estos estados acredita por sí solo la aceptación comercial.

| ID | Atributo de calidad | Escenario de calidad | Criterio de medida o comprobación | Trazabilidad y estado |
| :--- | :--- | :--- | :--- | :--- |
| AC01 | Seguridad y aislamiento multiempresa | **Estímulo:** un usuario intenta leer, modificar o recibir datos de otro negocio. **Contexto:** HTTP, reportes, soporte y eventos en tiempo real. **Respuesta:** la API valida empresa y permisos; PostgreSQL aplica RLS y las salas conservan su ámbito. | Probar dos negocios con roles diferentes: no se entregan datos ni se ejecutan cambios fuera de su ámbito. La cartera transversal se limita a plataforma y soporte autorizado; los roles operativos no usan SUPERUSER, BYPASSRLS ni TRUNCATE. | RNF-01; RF-01, RF-06, RF-10, RF-11 y RF-12. **Actual.** |
| AC02 | Autenticación y autorización coherentes | **Estímulo:** se revoca una sesión, se desactiva un usuario o se solicita una operación sin permiso. **Contexto:** personal conectado por REST y Socket.IO. **Respuesta:** el sistema deja de autorizar acciones con esas credenciales y protege las cookies de producción. | Comprobar rechazo de las operaciones afectadas en HTTP y tiempo real, sin cambios persistidos no autorizados; comprobar HTTPS y atributos HttpOnly y Secure. | RNF-02; RF-02, RF-06, RF-07, RF-09 y RF-11. **Actual.** |
| AC03 | Integridad y consistencia transaccional | **Estímulo:** llegan pedidos o cobros concurrentes, reintentos o una falla durante la operación. **Contexto:** pedidos, caja, inventario y fidelidad. **Respuesta:** el servidor recalcula importes en céntimos y confirma o rechaza la transacción completa; la idempotencia reconoce el reintento. | El mismo pedido reintentado mantiene una identidad y descuenta stock una sola vez; una clave reutilizada con otro contenido se rechaza. No se aceptan stock negativo, importes incompatibles ni referencias entre empresas; una falla no deja cobros ni descuentos parciales. | RNF-03; RF-04, RF-05, RF-07, RF-08, RF-09 y RF-12. **Actual.** |
| AC04 | Rendimiento y capacidad medida | **Estímulo:** aumenta la concurrencia de cartas, pedidos, cocina, caja y reportes. **Contexto:** una API Render Starter de 512 MB y 0,5 CPU. **Respuesta:** consultas paginadas, pool limitado, caché acotada y concurrencia controlada mantienen la integridad. | Un ensayo representativo conserva su versión desplegada, volumen de datos, mezcla de operaciones, concurrencia y duración; registra latencia p95, errores, memoria y conexiones. No debe haber reinicios por falta de memoria ni divergencias de pedidos, cobros o stock. Los umbrales de respuesta y error se acuerdan antes del ensayo; la capacidad admitida se publica junto con el perfil probado. No se atribuye un número de negocios al plan sin medir. | RNF-04; RF-02, RF-03, RF-04, RF-06, RF-07 y RF-10. **A validar.** |
| AC05 | Mantenibilidad y comprobabilidad | **Estímulo:** cambia una regla de negocio o un proveedor de persistencia, archivos o eventos. **Contexto:** backend monolítico modular con puertos y adaptadores como objetivo. **Respuesta:** casos de uso y contratos delimitan los módulos; las reglas de core conservan independencia tecnológica. | Las reglas de core no importan Express, Prisma ni SDK externos. Sustituir adaptadores por dobles permite probar los casos de uso sin cambiar las reglas; un módulo no accede directamente al repositorio de otro. | RNF-05; RF-02, RF-04, RF-06, RF-07, RF-09, RF-10, RF-11 y RF-12. **Objetivo.** |
| AC06 | Portabilidad del frontend | **Estímulo:** se prepara el traslado de Vercel a Cloudflare Workers Paid. **Contexto:** Next.js con OpenNext en workerd, antes de cambiar DNS. **Respuesta:** la versión compatible y la configuración de runtime preservan SSR, rutas, sesiones e integraciones. | Verificar dominio raíz, subdominios, proxy, Google Identity, cookies, fotografías y conexión Socket.IO. Validar `nodejs_compat` y el soporte experimental de `proxy.ts`; conservar una ruta de reversión y cambiar DNS solo después de aprobar las comprobaciones. | RNF-06; RF-01, RF-03, RF-06, RF-11 y RF-12. **A validar.** |
| AC07 | Disponibilidad y evolución controlada | **Estímulo:** la API se reinicia, falla o requiere mayor capacidad. **Contexto:** una sola instancia pagada, sin réplica de API ni balanceador adicional. **Respuesta:** los sondeos previstos detectan fallas y se recupera el servicio; el cliente relee el estado persistido al reconectar. | Comprobar `/salud/en-vivo` para vida y `/salud/listo` en release o verificación operativa. La arquitectura no promete continuidad ante la caída de la única API. Antes de agregar instancias se prueban coordinación de eventos, caché, límites, conexiones y afinidad de polling o WebSocket único. | RNF-07; RF-03, RF-04, RF-06 y RF-07. **Objetivo.** |
| AC08 | Recuperabilidad de datos y archivos | **Estímulo:** se pierden datos o archivos, o debe restaurarse una copia. **Contexto:** respaldo externo en R2 privado y proyecto de recuperación separado de Neon Launch. **Respuesta:** el job diario genera copias verificables; el ensayo semanal recrea esquema, roles, RLS, datos y referencias a fotografías. | Conservar siete copias diarias y cuatro semanales de la base; comprobar copias de archivos y avisos de falla. Registrar pérdida de datos y tiempo de restauración. Para usar la copia externa, RPO de 24 horas y RTO de 2 horas son **metas por ensayar**, no garantías. La base de recuperación no recibe tráfico comercial ni ofrece conmutación automática. | RNF-08; RF-04, RF-06, RF-07, RF-08, RF-09, RF-10 y RF-12. **Objetivo.** |
| AC09 | Observabilidad y protección de información | **Estímulo:** ocurre un error de aplicación, una indisponibilidad o un respaldo fallido. **Contexto:** API, frontend, jobs y paneles de los proveedores. **Respuesta:** logs con requestId, Sentry y alertas permiten relacionar la falla sin exponer información sensible. | Un error de ensayo aparece en Sentry con requestId y alerta; UptimeRobot realiza sondeos cada cinco minutos; un job fallido avisa. Revisar que logs y trazas no contengan cookies, tokens ni secretos. Un sondeo HTTP correcto no demuestra salud de PostgreSQL ni integridad de las operaciones. | RNF-09; RF-03, RF-04, RF-06, RF-07 y RF-10. **Objetivo.** |
| AC10 | Entrega y migraciones verificables | **Estímulo:** se publica una versión o cambia el esquema de datos. **Contexto:** CI/CD con credenciales separadas para migraciones y ejecución. **Respuesta:** las verificaciones bloquean releases fallidos; el release aprobado migra, despliega y comprueba el servicio. | Ensayar que un fallo de tipos, lint, pruebas o build impida publicar. Aplicar migraciones en una base vacía y probar con roles restringidos; preservar funciones `facipos.*`, RLS y restricciones SQL no representadas por Prisma. Comprobar operaciones y salud; documentar una reversión compatible con los cambios de esquema. | RNF-10; RF-01 a RF-12. **Objetivo.** |

La referencia técnica es la [arquitectura inicial del laboratorio](../arquitectura/arquitectura-inicial.md), que distingue implementación actual y arquitectura aprobada para el lanzamiento. Los identificadores RF conservan los del [catálogo de requisitos funcionales](03-requisitos-funcionales.md).
